1. Continuous Context Management：每一步都维护工作记忆，未必更便宜

来源：William Hoy 等，arXiv 研究论文。
首次发布日期：2026-09-28；arXiv Submission history 明确列出 v1：2026-09-28 16:20:08 UTC，不是修订日期。
主题：Context Management、工作记忆、执行循环、成本评估。
链接：论文与版本记录｜原文方法与实验

这是什么？

CCM 把“接近窗口上限才压缩”改成“每次行动都产出下一轮记忆”。下一轮只接收原始任务、保留的记忆和最新观察，不直接携带完整聊天轨迹。

核心贡献

  • Memory 成为执行循环的显式输出。 模型同时生成更新后的记忆与环境动作；旧信息能否继续影响执行，取决于它是否被保留下来。
  • 给出了重要的负结果。 Terminal-Bench 2.0 的 89 个任务上，累计输入减少约 76%—84%，但四个模型中三个成功率下降。Opus 4.6 从 58.4% 降至 40.4%。
  • Token 不是账单的替代指标。 计入 prompt caching 后，Kimi K3 的估算单任务成本从 $0.302 升至 $0.622，成功率仅从 62.9% 到 64.0%。论文进一步用 GRPO 与完整历史特权蒸馏改善紧凑记忆下的行动策略。

为什么重要？

它纠正了“摘要越短，Agent 就越高效”的直觉：记忆保真、行动能力、缓存命中率是不同问题，必须一起测。CCM 也没有压缩最新工具观察，因此单次巨大输出仍会撑大 prompt。

对 Agent / Coding Agent 架构的启发

把 模型可见的工作记忆 与 持久化事实、原始轨迹 分开。可以缩短下一轮 prompt，但不能因此删除执行日志，或把模型写的“已完成”当作真实的提交、测试和外部副作用状态。

对我的工程实践有什么启发？

在 Harness 中做一个可切换的 prompt assembler，对比完整历史、阈值压缩、逐轮记忆三种策略。记忆至少覆盖当前目标、代码版本、已验证结果、未解决问题；原始工具输出仍留在外部日志。评估同时记录任务成功率、漏掉约束的次数、缓存读写、总费用和延迟，先灰度实验，不直接替换默认策略。

与已有工作的关系

这是对 MEM1 类逐轮记忆思想的扩展与系统性评估，而不是“首次想到摘要”。对 Claude Code / Codex 类 Harness 的意义，是提供一种值得对照测试的执行状态设计，而非证明其默认上下文策略应该被直接替换。

2. Ingot：把工具结果变成可查询的事实层【回溯】

来源：tjbroodryk/ingot，MIT 开源项目；已阅读 README 与 benchmark 方法说明。
首次发布日期：2026-09-06；首个发布标签 v0.1.0 的注释明确写着 “the first published release”，annotated tag 原始时间为 2026-09-06 22:33:07 UTC，公开标签页一致。不把 09-28 的 Show HN 当作首发。
主题：Structured Memory、工具结果持久化、检索接口、Memory Eval。
链接：仓库｜首次发布标签｜评测方法

这是什么？

它把 Agent 的工具 JSON 投影成有类型的表，让模型通过 SQL、关键词或向量相似度取回证据，而不是只能在“塞满原文”和“返回若干相似片段”之间选择。

核心贡献

  • 支持跨工具计算。 PR、CI、服务归属等结果可以做关联、排序、聚合与缺失项查询；“哪些服务从未发生事故”不是一个普通相似度检索问题。
  • 写入与查询分层。 新记录先进入 Postgres overlay，随后汇入对象存储中的 Parquet；DuckDB 联合查询两层。存储与普通查询默认不需要模型调用，embedding、摘要和 OCR 按需启用。
  • 对照实验关注接口，而不只比较品牌。 同一数据、同一向量分别走 SQL 与 top-k；另外比较 MCP 和 REST，尝试拆分“数据模型优势”与“工具描述优势”。

为什么重要？

Coding Agent 经常需要的是准确的执行事实，而非一段相关文字。项目自报的 501 条记录、33 个问题、每题 3 次实验中，MCP/REST 准确率为 97%/96%，完整上下文为 90%；这是小型合成评测，不能外推成全面优于生产 RAG，且 schema 编写成本是实际代价。

对 Agent / Coding Agent 架构的启发

把 Memory 分成两类接口：解释和经验适合文本检索；测试结果、文件归属、任务状态适合结构化查询。向量检索仍有用，但不应被迫承担计数、去重或状态判定。

对我的工程实践有什么启发？

先抽出 工具结果投影器＋只读查询适配器，不要一开始复制整套存储架构。把 CI 结果、改动文件和任务记录映射成表，保留原始 payload 引用、仓库版本、采集时间和稳定 ID。用同一批任务比较 top-k 与 SQL＋检索，并把人工 schema 和模型生成 schema 分开计分。

与已有工作的关系

这是数据库、对象存储和 Agent 工具接口的工程组合，不是新的存储理论。最值得借鉴的是：用可证伪的对照实验，判断 Memory 应该暴露什么操作。

3. Your data context should be debuggable：让漏检有明确的修复位置

来源：Aloÿs Augustin，Cassis 原创工程博客。
首次发布日期：2026-09-28；原文 JSON-LD 的 datePublished 明确标注该日期，不采用 HN 转发时间。
主题：Context Management、渐进披露、检索可观测性、知识维护。
链接：原文

这是什么？

作者把数据 Agent 的业务知识组织成领域树：从根节点进入，每次只看到当前领域的规则和子领域简介。这样一旦漏掉关键规则，就能找到 Agent 在哪一个分叉走错。

核心贡献

  • 区分四类失败： 信息缺失、信息错误、检索失败、模型理解错误。它们不应该都靠“换一个更强模型”处理。
  • 把检索路径变成可修复的接口。 若 Agent 看见 billing 的描述却没有进入，就检查这个描述是否充分说明它与收入问题的关系。
  • 每条事实只有一个权威位置。 规则放在适用范围内最深的领域；跨域 join 引入表时，自动补齐尚未读到的祖先上下文，避免只拿到数据、漏掉解释规则。

为什么重要？

“知道正确规则在哪里”与“知道为什么没检索到它”是两回事。作者报告客户场景中加载 token 减少 50%—80%，但没有提供可独立复现的完整基准；更可迁移的是定位故障的方法，而不是这个百分比。

对 Agent / Coding Agent 架构的启发

给上下文加载增加 trace：看到了哪些候选、打开了哪条路径、哪些祖先规则自动进入 prompt。原文针对业务数据；迁移到代码仓库时，应优先用于架构文档、兼容性约束和模块知识，不必用领域树替代符号搜索或 grep。

对我的工程实践有什么启发？

做一个轻量 open_domain 工具，返回本域说明、子域描述、规则版本与证据链接；记录完整导航路径。给一组已知失败任务标出“必须读到的规则”，统计首次错误分叉和规则召回率。先修改那个分叉的描述，再重跑任务，而不是不断把全文追加到全局说明文件。

与已有工作的关系

这是 progressive disclosure 的工程化。它与文档树检索同源，但把树建立在业务知识和适用范围上，重点从“找得到”推进到“漏掉时修得动”。

4. Share-Borne AI Virus：文档可以把污染带过独立的 Memory 边界

来源：Sidharth Pulipaka 等，arXiv 研究论文；附开源实验仓库。
首次发布日期：2026-09-28；arXiv API 的 published 为 2026-09-28 16:34:52 UTC，原文标记为 v1。
主题：Persistent Memory、信任边界、跨会话状态、Agent 安全评估。
链接：论文｜原文｜实验仓库

这是什么？

研究的不是共享数据库被污染，而是几个互不共享记忆的个人助手：一个读入有问题的文档，把内容保存到 Memory；以后写另一份文档时又带出这些内容，随后被另一个助手读入。

核心贡献

  • 刻画“文档→记忆→新文档”的跨会话传播。 Agent 不必互相发消息，正常的人类文档交接就能连接原本隔离的系统。
  • 评测传播而非单次中招。 指标包括污染比例、传播跳数，以及只有错误目标被记住、还是连后续传播机制也被保留。
  • 给出了有条件的规模结果。 大型模拟采用 30 个助手、最多 60 个时间步、3 个种子文档；GPT-5.6 Luna 的目标污染覆盖达 60%—80%，实验中链条最深到 8 跳。主实验依赖攻击者外部端点协助及允许出站访问，不能等同于纯文本必然自传播。

为什么重要？

重启会话、拆分 Agent、分开存储 Memory，都不能自动撤销已经进入文档和持久状态的不可信信息。这些是模拟环境结果，不是现实世界感染率，也不是对所有 Coding Agent 产品的直接结论。

对 Agent / Coding Agent 架构的启发

Memory 写入本身不能提升信息的信任等级。外部文档中的陈述，不应因为被摘要进长期记忆，就被当成用户曾经下达的指令。来源、权限和后续出站动作需要分别控制。

对我的工程实践有什么启发？

给持久记忆保留来源文档、写入任务和信任类别；把用户确认的偏好与外部资料推断分开。对会改变未来行为的记忆写入增加确认门，对外部服务发送文档实行明确授权。先用无害哨兵标记、隔离测试环境构造两次文档交接，验证未经确认的内容不会升级成指令。

与已有工作的关系

它把单 Agent 的跨会话记忆污染，扩展到“独立私有记忆之间经产物传播”的场景。对 Harness 的提醒是：Sandbox 的边界不仅在进程和网络，也在状态写入与产物交接。

5. BaRe-Mem：把协作可靠性保存成可更新的状态

来源：Peilin Feng、Zhengyang Huang、Soujanya Poria，arXiv 论文及开源实现。
首次发布日期：2026-09-28；arXiv API 的 v1 published 为 2026-09-28 16:25:16 UTC。
主题：Agent Memory、协作决策、验证反馈、Worker Routing。
链接：论文｜原文｜代码

这是什么？

它不只存“某个顾问过去答对几次”，而是结合当前问题、候选答案和来源，维护顾问在这个上下文中的可靠性；同时估计主 Agent 自己解决问题的能力。

核心贡献

  • 用验证结果更新记忆。 Bayesian reliability memory 随已核实的正确/错误结果在线更新，不把模型的自信表态当作正确性标签。
  • 既决定相信谁，也决定是否采纳协作结果。 原方法按可靠性调节顾问文本的 attention，并比较咨询与自主推理的预期收益；给所有顾问重新加权，不代表他们整体值得信任。
  • 延伸到任务路由。 除九个 benchmark、六个中心模型的咨询实验外，还在 MuSiQue 上评估 worker 选择：可靠性状态帮助更早找到能解决子任务的 worker，而不是多试几遍所有人。

为什么重要？

协作并非单调增益。在受控误导实验的困难任务组中，Qwen3-14B 面对最高误导设置时，普通 peers 输入准确率为 50.6%，BaRe-Mem 为 68.6%，自主推理为 66.5%。这支持“保留不采纳建议的选项”，但不是 repository-level coding 的成绩保证。

对 Agent / Coding Agent 架构的启发

Memory 也可以是调度器的能力模型：记录哪类任务上哪个 worker 更可靠、判断有多不确定、证据是否经过验证，而不只是自然语言经历。

对我的工程实践有什么启发？

先做外部路由层实验：记录任务类别、worker、实际验证结果及调用成本，对比无记忆路由、历史成功率路由和上下文相关路由，保留“主 Agent 自己处理”的选项。原论文的 hidden-state 特征和 attention 修改需要内部模型访问；对 Copilot、Claude、Codex 等闭源 API，只能先借鉴路由思想，不能声称完整复现。

与已有工作的关系

它从 majority vote / debate 转向“经验证的历史可靠性控制当前协作”，是 Memory 与 Feedback Loop 的结合；收益最终取决于验证器是否可靠，而不是参与的 Agent 数量。

Engineering Takeaways

如果本周只给自己的 Coding Agent / DeepSeek Harness 类系统加实验，优先做这五个：

  1. 工作记忆 A/B 开关。 不动权威执行日志，只切换模型可见历史；同时测成功率、约束遗失、缓存和实际账单，避免只优化 token 数。
  2. 结构化工具记忆。 先把 CI、文件归属和任务状态接入只读 SQL；语义材料继续走检索，用同数据、同预算判断组合是否更好。
  3. 可回放的上下文导航。 记录检索分叉和祖先规则，建立“必要规则未读到”的失败集；把修复定位到一条描述，而非整个 prompt。
  4. 带来源的 Memory 写入门。 外部信息不能自动变成用户指令；用无害的跨会话、跨产物用例检查信任升级和未授权出站行为。
  5. 会拒绝无效协作的路由器。 用测试、CI 或其他独立验证信号更新 worker 可靠性；除了“找谁”，还要测“这次是否值得采纳别人的意见”。

本期主线判断

本期三条工作是 Agent「执行状态」的三种载体：

  • CliffCompaction：原始 transcript 本身继续充当状态，只在超过阈值时，用确定性、可丢弃、可重算的“动作日志”替换历史前缀。

  • 模型只能引用 runtime 已经展示给它的 id。

这是什么？

一个本地 HTTP 代理，放在 coding agent 和模型 API 之间，支持 Anthropic Messages、OpenAI Chat、OpenAI Responses 三种协议。

  • 平时：请求原样透传。
  • 超过阈值时（一次“cliff”）：把最近 keep_recent 个 turn 之前的历史，用纯函数、不调用 LLM 的方式，折叠成一条 user 消息——一份“动作日志”。
    • 保留：thought、tool call 签名（截到 150 字符）、500 字符以内的 tool result、人类消息。
    • 丢弃：更长的 tool result 整段丢掉，agent 需要时自己重新 cat / grep。
  • 之后：代理用消息哈希链记住“这段前缀已被哪条摘要替换”，后续请求总是发送同一个 [head, summary, 新 turn…] 前缀。

效果是：两次 cliff 之间 prompt cache 持续命中，每次 cliff 只付一次 cache 失效。context 大小呈锯齿形——“cliff”由此得名。

核心贡献

  1. 把“要不要压缩”改写成“cache 账单怎么算”。 Table 7（TB2.0，GLM 5.1，按“理想缓存”口径记账）：

    • 不压缩时，cache read 占总账单 78%。
    • Cliff 把 cache read 从 $0.427 降到 $0.087（−80%），总成本从 $0.548 降到 $0.268（−51%）。
    • 多出来的 uncached input 和 output 只有约 $0.06。

    也就是说，收益来自“被反复重读的前缀变短了”，成本来自“cache 失效的次数”。在论文所用 provider 的价格下，uncached input 约是 cached 的 5–6 倍。

  2. 确定性压缩。 同样的消息序列一定得到同样的摘要。代理重启、LRU 淘汰、中途接入的会话都能重算出相同的结果，不需要持久化，也没有摘要模型的幻觉问题。

  3. 丢观察，留动作。 context 构成里 tool result 占 56.0%、tool call 占 28.0%、thought 占 13.6%。Cliff 保留“做了什么、为什么做”，丢掉“看到了什么”，重新观察交给 agent 自己——文件系统就是外部记忆。

  4. 透明代理、失败即透传、有 shadow 模式。 不用改 scaffold，Claude Code、Codex、OpenHands、mini-swe-agent 都能接。prepare 出异常就原样透传；shadow 模式只记录“本来会发多少 token”。

def prepare(msgs):
    chain = chain_hashes(map(digest, msgs)); out = msgs; base = None
    for i in reversed(range(len(msgs))):                    # 最长前缀优先
        e = store.get(chain[i])
        if e and e.cut == i + 1:
            out = msgs[:e.head_len] + [e.summary] + msgs[e.cut:]; base = e; break
    if est(out) > T:
        compact_chain(base)                                 # proactive
        for rung in ([1, 2, 3] if strict else [1, 2]):
            if est(out) <= T: break
            truncate_summary() if rung == 3 else compact_chain(base, force=True, cfg=rung_cfg(rung))
    return out

def compact_chain(base, force=False, cfg=CFG):
    # 从 base 往后逐条“重放”，每越过一次阈值 compact 一次：
    # 无论历史是一次性到达还是逐步增长，得到的都是同一份“只含上一周期”的摘要
    working = (head + [old_summary]) if base else []
    for m in msgs[orig_cut:]:
        working.append(m)
        if chars(working) > T * 4 and (r := compact(working, cfg)):
            orig_cut += r.cut - (head_len + 1)              # 映射回原始坐标
            working = r.messages
    store.put(chain[orig_cut - 1], Entry(head_len, r.summary, orig_cut))

def compact(messages, cfg):
    head = messages[:first_assistant]  # 去掉末尾的旧 summary / system
    turns = group_turns(rest)          # 每条 assistant 消息开启一个 turn
    old, keep = turns[:-cfg.keep_recent], turns[-cfg.keep_recent:]
    parts = [line for m in flatten(old) for line in summarize_message(m, cfg)]
    # assistant：thinking:…（keep_thinking）、assistant:…（≤ thought_max_chars）、[Bash] {...}[:150]
    # user：旧 SUMMARY → []（整条丢弃）；人类文本 → user:…（≤ 20000）
    #       tool_result ≤ 500 字符 → result:…；更长 → 丢弃
    S = user_message(SUMMARY_HEADER + "\n\n" + "\n\n---\n\n".join(parts))

设计取舍分析

作者的取舍

  1. 用确定性换语义理解。 App. C.1（SWE-bench Verified，Kimi K2.7，16K）统计了相对 full context 多出的 re-read 次数：
    • Cliff +5.04、microcompaction +4.68、sliding window +3.80、LLM summarization +2.35（后者步数只多 1.26）。
    • 作者的解读：意译让 agent 满足于二手信息，不再回看原文件。所以 Cliff 让 agent“多读几次”，某种程度上是把它逼回 ground truth。
  2. 准确率不是全胜。 SWE-bench Verified 16K 下，sliding window 72.80 略高于 Cliff 的 71.33，但成本 +9%，Cliff 是 −21%。KernelBench L3 上 Cliff 为 3.58× / $8.32，microcompaction 为 3.33× / $12.84。
  3. 只保留上一周期的摘要。 _summarize_user 遇到 SUMMARY_HEADER 直接返回 []。好处是摘要有上界，从任意起点重放结果都一致；代价是信息最多只能活过一次 cliff。
  4. 阈值控制的是 cache 失效频率，而不是 context 长度。 Table 8 的真实账单并不单调：
    • SWE-bench + Kimi K2.6：32K +0%、16K −8%、8K +1%。
    • TB2.0 + GLM 5.1：−40%、−55%、−72%。
    • 阈值越紧，cache 命中率越低：GLM 在 TB 上从 79% 降到 47%。

本质 vs 权宜

  • 本质设计：
    • 前缀稳定是一等约束；
    • 压缩是可重算的纯函数；
    • 丢观察、留动作；
    • 任务头原样保留；
    • 评估按 cache 计价。
  • 权宜实现：
    • chars/4 估算 token；
    • 500 / 150 / 300 这几个魔数；
    • 只保留一个周期的摘要（可以换成分层摘要）；
    • 代理形态（长期看应内建进 harness）；
    • 进程内 LRU。
  • 论文与代码不一致：§2.2 说 thought 截断到 300 字符，但 config.py 默认 thought_max_chars=0（不限），300 只在 rung2 生效。复现论文结果需要设 CLIFF_THOUGHT_MAX_CHARS=300。

会失效的条件

  1. 会话中途的用户指令。 只有 head（system 和第一条任务）是永久的。中途的人类消息只会在下一次 cliff 的摘要里保留一次，再下一次就被丢掉。
    • benchmark 都是单任务，测不出这个问题；但在交互式会话里，“不要改 tests/”这类约束在两次 cliff 后就会消失。
    • seed 台账中的 2608.22752《The Compaction Cliff in Long-Running AI Agent Memory》测得：Claude Code /compact 一轮后安全规则保留 53%，五轮后只剩 10%。Cliff 的结构性保留率在第二轮就是 0。
  2. 信任降级。 500 字符以内的 tool result（可能来自网页、issue 或依赖包，都可能被攻击者控制）会被写进 user 角色的摘要，扩大了 prompt injection 的攻击面。
  3. 不可重取的观察。 非幂等或随时间变化的工具（线上 curl、跑 30 分钟的测试、会轮转的日志）重新获取要么很贵，要么结果不同。
  4. 中文等 CJK 负载。 chars/4 会低估 token 数，store.py 的 entry_size 注释也承认 CJK 要贵 2–4 倍。实际会越过阈值，只能靠 reactive 路径兜底。
  5. scaffold 自身的行为。
    • README 要求关闭 scaffold 自带的 compaction，因为原地改写历史会破坏前缀匹配。
    • 客户端看到的 usage 很小，本地历史会无限增长并每次全量上传，带宽和每请求 O(n) 的哈希开销随会话线性上涨。
  6. （推断，未验证）子代理共享 cache。 Anthropic 09-24 的博客说，Claude Code 的 forked subagent 会从父会话的 cache 起步。如果代理在父子请求中把摘要注入到不同位置，这种共享可能失效。

对 Agent / Coding Agent 架构的启发

  • Architecture：context 管理应该是一个有明确不变量的组件（前缀稳定、确定性、可重算），而不是“快满了就让模型总结一下”的 hook。

  • Runtime：cliff 的时机本身是个调度问题。Anthropic 同一篇博客建议“Compact before you step away rather than after”——cache TTL 一过，cache 本来就会失效，这时做 cliff 的边际成本接近 0。

    • 推论：触发条件可以设为 est > T_hard OR (est > T_soft AND idle ≥ cache_ttl)。

  • Memory：执行状态实际上被分成三层：

    • head：永久保留；
    • 摘要：只活一个周期；
    • 环境：无限但需要重取。

    缺少第四层：一份能跨 cliff 保留的“约束与决策账本”。

  • Context：长 tool result 是 context 中最大、也最容易重新获取的部分。LOHA/ACD 2609.31430 的标题《Compress What You See, Not What You Say》是同一个方向。

  • Tools：工具应声明 refetch_safe / idempotent 元数据，compactor 才知道哪些能丢。

  • Evaluation：同时报告“理想缓存”账本和真实计费账单，再加上 re-read 次数、步数、墙钟时间。GPT 版今天覆盖的 CCM 也明确说，省下的钱“强依赖 provider 的 prompt caching 策略与价格”。

  • Feedback loop：同一路径被反复 re-read，是“压缩过度”的免费信号。

开源实现：无官方代码。arXiv HTML 里的仓库链接都指向 baseline（mem0、tau2-bench、ZipAct、MemoryArena）。以下拆解依据论文正文、Algorithm 1 和附录 B.3 的完整 prompt 模板。

这是什么？

FlowState 不把完整的历史 transcript 喂给 agent，而是让模型每一步输出一个状态增量，维护一张 typed state graph（Active State）：

  • 之前请求的状态，只以“id + 一句摘要”的形式出现在索引里。需要时由模型点名，下一步才披露全文。
  • 每一步只能看到最新一条观察。旧观察只有被某个状态引用时，才会作为证据保留下来。

核心贡献

  1. 三层状态：
    • M_k：持久库，不进 context；
    • G_k = Index(M_k)：只含 id + 摘要的索引；
    • S_{k,t}：Active State，包括当前请求的状态和已披露的历史状态。
  2. ISU（增量状态更新）：模型只输出 add / update / remove。历史状态不可修改，只能新增一个带 supersedes 的状态来修正。
  3. PSA（渐进状态访问）：模型在 <state_focus> 中点名 id，runtime 校验这个 id 可见后才披露，披露的内容从下一次调用开始可用。
  4. 五类状态 + 四种关系：
    • 类型：preference / knowledge / attribute / judgement / artifacts；
    • 关系：supports / derives / follows / supersedes。
  5. 实证（底模 DeepSeek-V4-Flash，关闭 thinking，与同模型 full context 对比）：
    • τ³-Bench Airline：pass rate 从 58.0 提到 78.0，token 减少 61.2%。
    • τ³-Bench Retail：从 73.7 提到 81.6，token 减少 22.2%，但 Action Accuracy 下降 4.9pp。
    • MemoryArena 四个环境合计 token 减少 43.2%，9 项指标中 8 项领先。
    • 换成 GPT-5.6-terra 和 Qwen3.5-397B-A17B，相对 token 用量低 28.3%–56.3%。

机制拆解

① 数据结构

type StateType = "preference" | "knowledge" | "attribute" | "judgement" | "artifacts";
type Rel = "supports" | "derives" | "follows" | "supersedes";   // 边从 source（本状态）指向 target
interface StateNode {
  state_id: string; type: StateType; summary: string; value: Record<string, unknown>;
  refs: { rel: Rel; state_id: string }[];
  source_request: number; historical: boolean;   // 请求结束后 historical=true，之后不可 update/remove
}
interface StepOutput {        // 四个块必须全部输出，顺序固定，ΔS / R / z 至少一个非空
  state_focus: { target_id: string; reason: string }[];                      // R
  state_delta: { state_set: StateType; operation: "add" | "update" | "remove";
                 state_id: string; summary: string; value: object;
                 refs: { rel: Rel; state_id: string }[] }[];                  // ΔS
  tool_calls: { name: string; arguments: object }[];                         // z
  assistant_message: { content: string | null };
}

② 执行循环（按 Algorithm 1 还原）

for k, q in enumerate(requests):
    G = index(M); S, O = {}, None
    while not done(q):
        C = serialize(q, O, G, S)          # O 只有最新一条观察；每一步重建 context
        dS, R, z = policy(C)
        S = commit(S, validate_upd(dS, P, S))   # 历史 id 不能 update/remove
        R = validate_acc(R, P, G, S)            # R ⊆ ids(G) ∪ tool_refs(S)，且尚未披露
        S = S | disclose(M, S, R)               # 披露全文，related_states 只给 id
        O = execute(z) if z else None           # 依赖新披露内容的动作推迟到下一步
    M = persist(M, S)     # 新状态转为历史；被引用的原始 tool 结果作为证据节点保留

③ 单个历史节点的可见性状态机

[indexed：G_k 中只有 id + summary]
   │ state_focus 点名，且 validate_acc 通过
   ▼
[disclosed：全文和 related ids 进入 S；本步不能使用]
   │ 下一次调用
   ▼
[usable：可以被 refs 引用，但不能修改]
   │ 需要修正
   ▼
[被新节点 X supersede（X --supersedes--> 本节点）；原节点永不删除]

④ 上下文布局：稳定的 system（规则、策略、工具）+ 每步由 serialize 重建的状态块（q_k、索引、Active State、最新观察）。能命中 prefix cache 的基本只有 system 部分。

设计取舍分析

作者的取舍

  1. 用“每一步都记账”换“context 不随步数线性增长”。这要求模型有较强的格式遵循能力。
  2. 披露的内容延迟一步才能用。runtime 因此很简单，但每访问一次历史就多一次模型调用。
  3. 历史不可修改，有完整的审计链，但错误状态只能被 supersede 遮蔽，不能删除。
  4. 观察用完即弃。这是省 token 的主要来源，也是最大的风险：到达那一步没被引用的观察，就永远丢了。

本质 vs 权宜

  • 本质设计：
    • 可寻址的状态节点；
    • 两级可见性（索引常驻、全文按需）；
    • 历史不可变 + supersede；
    • 模型只能访问已展示的 id。
  • 权宜实现：
    • 五类状态划分（偏向对话和事务型任务）；
    • 延迟一步的披露；
    • 每一步重写上下文；
    • 用自定义 prompt 协议而不是原生 tool calling 来承载状态操作。

会失效的条件

  1. 统计功效不足。
    • travel 的 SR 0.74% 是 270 个任务中的 2 个；shopping 的 5.33% 是 150 个中的 8 个。
    • 没有报告方差，也没有重复运行。physics 只有 20 题、math 40 题，一题就能让分数变动 5pp 或 2.5pp；airline 的 +20pp 相当于 10 个任务。
  2. token 口径不考虑 cache。 full context 天然有很高的前缀命中率，而 FlowState 每一步都重写上下文。按真实账单算，优势会缩小，缩小多少未知。
  3. 观察丢失。 在仓库级 coding 中，“当时看起来无关、三步之后才发现关键”的输出很常见。
  4. 错误会持久化。 被注入的内容一旦写成状态，就会跨请求传播。
  5. 消融有反例。 Table 3 中，去掉 PSA 后 Shopping 的 PS 反而更高（44.67 对 42.89），只是 SR 更低，token 多约 2.6 倍——PSA 主要在省 token。去掉 ISU（改成在请求边界按规则建节点）后，SR 降到 0——执行过程中的持续记账才是核心。

对 Agent / Coding Agent 架构的启发

  • Memory = Execution State：计划、已确认的事实、待处理的风险，应该是有 id 的节点，而不是散落在 transcript 里的自然语言。
  • Context：“索引常驻、全文按需”适用于跨 session 记忆、子代理产出和长日志。
  • Runtime：Validate_acc 是很便宜的安全阀，模型编造的 id 会被直接拒绝。
  • Verification：judgement 类节点天然就是验证点。可以检查每个新 judgement 是否有 supports 边指向 knowledge 类证据。
  • Evaluation：token 口径必须改为按 cache 计价，这与 Cliff 的结论一致。

这是什么？

一个 Claude Code、Codex CLI、Hermes 共用的跨 session 记忆库：

  • 存储：一条记忆就是一个 markdown 文件（<type>/<group>/<name>.md），frontmatter 记录有效期、链接、权重和出处。所有索引都可以删掉重建。
  • 写入：由 session 边界的 hook 触发，先完整归档 transcript，再在后台蒸馏，不依赖 agent 自己去写。
  • 读取：三条通道——启动时注入 MEMORY.md、BM25 召回、直接 ls / grep。
  • 整理：独立的“睡眠”（sleep）流程。

核心贡献

  1. 单一事务写入路径。 所有写入都经过 _write_one：

    • 校验 schema、有效期、链接、出处；
    • 拒绝“事实日期晚于证据”的记录；
    • 事实变了必须写 successor；
    • 用临时文件 + os.replace 原子写入，用 source_hash 做乐观并发控制；
    • 批量写入失败时从快照回滚。

  2. 水位线：consumed（已归档）和 distilled（已蒸馏）分开记。代码注释写道“A missed hook costs latency, never knowledge”——漏掉一次 hook 只会延迟，不会丢知识。

  3. LLM 只负责出文本，库决定信什么。 蒸馏和睡眠用宿主 CLI 的无头单轮调用（HostReasoner 设置 tools_enabled=False，Claude 会带上 --tools ""）。

    • 需要查询时由库代为执行（模型输出 JSON 键 look，最多 3 轮）。
    • 只接受对账单（sheet）里出现过的 handle；邮箱地址必须能在证据中找到。

  4. 有上限的治理。 睡眠分两层：

    • T0 确定性整理；
    • T1 由 LLM 裁决提案，每次睡眠的上限是 merge 3 / supersede 5 / split 2 / delete 3。

    每次睡眠写一份决策账本和报告，并做一次 git commit。物理删除只有人工执行 mem gc 才会发生。

  5. 跨宿主可移植：3 个宿主之间 9 种有序写/读组合全部通过。

    path = placement.resolve(spec)                    # 重名时自动变成 name-2, name-3…

设计取舍分析

作者的取舍

  • 文件优先于数据库：可以 grep、可以进 git；代价是并发只能靠 fcntl 锁和乐观哈希，适合个人或团队规模。
  • 写入由系统保证覆盖：代价是依赖宿主的 hook 体系。
  • 库里不内置 LLM 客户端：没有第二份账单，推理过程可以在宿主 transcript 里审计；代价是质量受宿主默认模型影响（Claude 路径是 Haiku 4.5，Codex 路径是 gpt-5.6-sol）。
  • 向量检索默认关闭：README 的实测里，Recall@5 从 79.0% 提到 86.6%，但中位延迟从 5.1ms 升到 139.2ms，端到端没有收益。

本质 vs 权宜

  • 本质设计：
    • 单一写入路径 + supersede 链 + --as-of；
    • 先归档再蒸馏的水位线；
    • 可重建的索引；
    • LLM 提议、库来裁决；
    • 无人值守的操作有上限。
  • 权宜实现：
    • 只支持 POSIX（locking.py 在顶层 import fcntl，hook 使用 SIGALRM / setitimer），Windows 原生不可用；
    • 各种魔数；
    • 硬编码的默认模型。

README 与代码不一致：README 说“删除只以提案形式等你确认”。但 sleep(reasoner) → _review 的实现是：只要传了 reasoner（mem sleep --reason host），LLM 每次睡眠最多可以接受 3 个删除提案。这些删除是软删除（写入 invalid_at，可以通过 --as-of 找回）。更准确的说法是：删除可以无人值守，但有上限、是软删除、可以恢复。

会失效的条件

  1. Windows 原生环境无法运行。
  2. 语义层面的投毒：红队测试覆盖了指令注入、路径穿越、畸形 frontmatter 等，但一条“看起来合理的错误事实”仍然能写进去，只能靠 supersede 链事后追溯。
  3. MEMORY.md 容量：8192 字节的上限会挤掉冷门但关键的约束。
  4. 评测范围有限：LongMemEval-S 的 haystack 被限制在每个 episode 12 个 session。52.9% 对 MemCore 35.8% 是端到端对比，不能归因到读或写单独一侧（README 自己也这么说）。

对 Agent / Coding Agent 架构的启发

  • Memory：跨 session 记忆的关键是写入治理：单一路径、出处、有效期、successor、上限、可撤销。
  • Runtime：捕获要同步完成（便宜、不能丢），蒸馏要异步进行（昂贵、可以慢）。
  • Tools / Sandbox：处理不可信的 transcript 时，“不带工具的单轮 LLM + 由库代为执行查询”是最小权限的形态。
  • Evaluation：除了 QA 准确率，还要测跨宿主互通、写入覆盖率和红队治理。
  • Feedback loop：access log → 权重 → 常驻注入集合，形成一条由使用驱动的遗忘曲线。

对 Microsoft 员工和工程师的影响：模型选择成了日常的成本决策——同一个任务，用 Sonnet 5.5 可能只要 Opus 5.5 一半的钱。会做模型路由和评估的人更有价值；团队之间比的是 harness 质量，而不是接入了哪个模型。

我的判断：护城河正在从“独家拿到 OpenAI 模型”转向“分发最广、企业治理最完整”。但模型厂商自己的产品，比如 Claude Code 和 Codex，会和 Copilot 竞争得更直接。

5. Morgan Stanley Views

① Mike Wilson（9/28）：市场宽度和指数“在中间会合”（Investing.com/Yahoo）

  • MS 观点：“如果债市波动不平静下来，我们倾向于认为两者会在中间会合。”也就是说，未来一个月宽度和指数会收敛，然后年底强势收官；如果波动更早回落，宽度会追上指数。
  • 核心逻辑：
    • 市场并不自满：罗素 3000 中超过一半的股票自 6 月以来跌了至少 20%，标普 P/E 回到约 19 倍，而中位数个股的 EPS 增速仍在十几个百分点。
    • 宽度收窄的起点是 Jackson Hole：之后市场开始定价更鹰派的 Fed，动量因子经历了史上最严重的回撤之一。
    • 配置上偏好大盘质量股、轻资产、盈利预期上调的公司；如果指数下跌，会加仓风险资产。
    • 重度使用 AI 的公司利润率更好，而一致预期假设这种优势会消退，所以还有上行空间。
  • 我的分析：今天的数据加上 5.24% 的 10 年期收益率，说明“债市波动平静”这个前提还不成立，指数下跌去迎合宽度的可能性在上升。“AI 利润率优势”这一点支持 MSFT 这类平台公司，但要等 10 月下旬的财报来验证。

② MS 对 Micron 的财报前瞻（二手）

  • MS 观点：评级 OW，目标价 1,200 美元。近期基本面“仍然非常好”；财报后预期会上调，但幅度小于前几个季度。原话是：“关于周期能持续多久的争论需要更长时间才有结果，短期内没法证明。”
  • 我的分析：公司给的 FQ4 指引是收入 500 亿 ±10 亿、毛利率约 86%、EPS 约 31 美元，基数已经非常高。市场真正看的是 FQ1 指引和 HBM 价格的边际变化。“好但边际放缓”这个判断，和周一存储股大跌时反映出的周期见顶担忧是一致的。

③ Seth Carpenter：MS 的基线是 12 月和明年 3 月各加一次息（前几期已介绍），而市场给 10 月加息约三分之二的概率。明天的 PCE 和周五的非农会检验谁对。
